# 抖音小程序版规划（2026-08-08）

> 前提：微信小程序 v1 已上线（AppID wx213d47a529c7055c），多平台策略见 `2026-08-多平台拓展调研与策略.md`（抖音=P1，阶段 2 千川直购放大）。本文回答"怎么做"：移植路线、差异清单、平台前置、节奏。
> 工作区已就位：`douyin` 分支 + worktree `/Users/app/LuckyNemo-Wedding-douyin`。

## 〇、核心判断

**抖音是移植成本最低的第二平台**。字节小程序框架与微信近 1:1（TTML/TTSS/JS、`tt.*` 对 `wx.*`、app.json 同构），不像小红书是独立框架必须重写。15 个页面可整体复制 + 机械替换 + 适配层，真正的开发量集中在三个通道：**登录、支付、分享**。

后端架构有红利：worker / OSS / catalog / 模卡管线全部与平台无关（openid 只是字符串前缀），需要动的只有 `app.py` 新增 douyin 通道接口。

**最大的产品差异是支付模型**：抖音没有微信式"虚拟代币"体系，担保支付是**按单支付**。微信端的"金币钱包（充 4 币买 1 张）"模式在抖音不成立，定价要改成"单次下单直接付"（4 元/张、52 元/20 张套餐直接担保支付下单）。**iOS 端完全没有虚拟支付通道**（[官方社区回复](https://forum.microapp.bytedance.com/mini-app/posts/6642d5b9ed3a59e1785547ea)，且审核会拒任何引导文案——包括"去安卓支付"类提示），iOS 只能给免费体验额度。

## 二、移植路线（阶段 1，约 1–2 周）

新建 `miniprogram-douyin/`（命名对齐 xhs 先例），整体复制 `miniprogram/` 后分四层处理：

1. **机械替换层**（占 90% 工作量，基本是体力活）
   - `.wxml→.ttml`、`.wxss→.ttss`、app.json/project.config.json 同构改 AppID
   - `wx.*` → `tt.*`（request/login/uploadFile/downloadFile/saveImageToPhotosAlbum/canvas/showModal/showToast/navigateTo/setStorage 等基本对齐）
   - 写一个 codemod 脚本批量做，再人工过一遍 diff

2. **通道适配层**（真正的开发量）
   - **登录**：`tt.login` code → 后端新增 `/api/dy/login`（字节 `apps/v2/jscode2session` 换 openid/session_key），openid 前缀 `dy-`；session 表复用 mp_sessions 模式
   - **支付**：弃用金币/代币。新增 `/api/dy/pay/*`：预下单（担保支付 create_order，SALT 签名）→ `tt.pay` 收银台（抖音支付/微信/支付宝三渠道）→ 异步 notify 回调验签到账。**幂等设计照抄微信 confirm 的经验教训**
   - **iOS 分端**：前端 `tt.getSystemInfo` 判 iOS → 隐藏一切付费入口与文案（连"iOS 暂不支持"的引导语都可能被拒审），只留免费额度体验
   - **分享**：抖音无朋友圈，分享出口=私信/群卡片 + `tt.showShareMenu`；获客主链路是**短视频挂载小程序锚点、直播间小雪花、搜索**——裂变归因（?ref=/scene）机制要按抖音 scene 重做，**第一版建议直接砍掉裂变，直购闭环优先**

3. **能力差异清单**（逐个替方案，提审前必须清零）
   - `button open-type="contact"`（微信客服）抖音没有 → 抖音有客服消息能力，改对应入口
   - `open-type="share"`、小程序码（wxacode.getUnlimited）→ 抖音有自己的二维码接口
   - web-view 业务域名、人脸核身（微信原生能力）→ **人脸认证链路是最大未知数**：微信端用的真人认证在抖音需要找替代（自研上传+人工/第三方核身），方案待调研确认
   - 保存相册、canvas 海报：接口基本对齐，注意权限声明差异

4. **后端复用**（跨组文件，改动前群里同步）
   - `server/app.py`：新增 `/api/dy/*`（login、pay、order 复用）；mp_orders/mp_jobs 表加 `channel` 字段（wx/dy）区分来源
   - `server/mp_worker.py`：**零改动**（任务队列与平台无关，openid 前缀不同而已）
   - 模卡 catalog、定妆、三视图、九宫格系列、品控兜底全部直接可用

经验教训前置（微信端踩过的坑，别重踩）：**前端改动必须先在抖音开发者工具验证再累计**（微信 v4 批次 4 批未验证集中爆雷）；支付链路先沙箱/体验版真机跑通再谈放量。

## 四、风险与未决

1. **iOS 无支付是结构性天花板**：抖音客群安卓占比高可接受，但 iOS 用户只能免费体验。不要做任何引导话术（审核红线），转化全靠安卓直购 + 抖音搜索/私信自然流量。
2. **人脸核身替代方案未调研**：微信端真人认证依赖微信原生能力，抖音端怎么做人像授权核身（自研/第三方/放宽为协议授权）需先出结论再动 makeup 相关页面。
3. **担保支付的虚拟商品口径**：抖音电商 2026-02 起虚拟类目收紧（动态保证金），"AI 生成图片服务"算哪个类目、保证金多少，进件时确认。
4. **AIGC 类目审核材料清单**（多平台调研未核实项）：提审前找平台行业运营确认，避免反复打回。
5. **裂变机制不搬**：微信"邀请有礼"依赖微信社交链，抖音场景完全不同，首版不做，等直购闭环跑通后再设计抖音原生玩法（评论区组件/搜索口令等）。
